# DataVault frontend handoff (Render staging)

The staging API base URL is `https://datavault-saas.onrender.com`. There is **no `/api` prefix**. Set `NEXT_PUBLIC_API_URL=https://datavault-saas.onrender.com` in the frontend. Interactive API documentation is at [Swagger](https://datavault-saas.onrender.com/docs), and its OpenAPI JSON is at `/docs/openapi.json`. Process health is `/health/live`; MongoDB readiness is `/health/ready`. Render Free can cold-start after inactivity, so allow for an initial slow response. These URLs identify staging, not a production SLA.

## Authentication and onboarding

Tenant authentication is a one-hour Bearer JWT returned by `POST /auth/sign-in` (HTTP 201, `{ "accessToken": "…" }`). Send it as `Authorization: Bearer <tenant-jwt>` for protected tenant routes. `GET /auth/current-user` returns the current user. Do not use the separate Platform Admin JWT for tenant APIs. Sign-in and protected tenant requests reject inactive or suspended companies. Do not persist JWTs in shared examples, screenshots, logs, or source code.

`POST /auth/sign-up` (HTTP 202) accepts `companyName`, `email`, `password`, `country` (ISO 3166-1 alpha-2), `industry`, and optional `fullName`. It creates an inactive company, its owner, and a Free subscription, then requests an activation email. It does **not** issue a JWT. The email contains a single-use `token` query parameter. A frontend activation page must read that parameter and submit `{ "token": "…" }` to `POST /auth/verify-account` (HTTP 200). A reused, invalid, or expired token returns HTTP 400. Activation tokens expire after 24 hours. `POST /auth/resend-verification` accepts `{ "email": "…" }` and returns a generic HTTP 202 response; it has a cooldown and rotates the token when eligible. The frontend should then send the user through normal sign-in.

Workspace password recovery is separate from platform admin recovery. Public `POST /auth/forgot-password` accepts `{ "email": "…" }` and always returns a generic HTTP 202 response for valid email input. Eligible active users receive a 30-minute, single-use link to `/reset-password#token=<token>`; requests have a 60-second per-account cooldown. The frontend removes the fragment from browser history immediately, then submits `{ "token": "…", "newPassword": "…" }` to public `POST /auth/reset-password` (HTTP 200, `{ "reset": true }`). Every new workspace or platform-admin password (signup, invitation, recovery, setup, and change) must be 12–72 characters, include uppercase and lowercase letters, a number, and a symbol, and use no more than 72 UTF-8 bytes. Sign-in accepts existing passwords up to 72 characters, including passwords created under the previous rule. Invalid, expired, or reused links return HTTP 401. A successful reset invalidates earlier tenant JWTs; the user signs in again. Neither endpoint accepts a platform admin JWT or sends one in response.

The local frontend has an `/activate` page. Before a live email demo, point staging `ACCOUNT_ACTIVATION_URL` to its deployed HTTPS URL; the previously configured staging URL was a placeholder. Do not open a placeholder link or send its token to that host. Never paste a token into chat, commit it, or put it into a shell command or shared API collection. Use an accessible address you control and a unique disposable company. If signup returns HTTP 503 because delivery failed, registration was still saved: investigate delivery and use the generic resend route rather than repeating signup with the same identity.

Company owners invite employees with `POST /invitations` using `{ "email": "…" }` (HTTP 202). The email link likewise has a `token` query parameter. An invitation page must submit `{ "token": "…", "fullName": "…", "password": "…" }` to public `POST /invitations/accept` (HTTP 200), then direct the employee to sign in. The backend assigns company and `company_member` role; neither is client-selectable. Invitations expire after 72 hours and are single-use. Owners can list, resend, or revoke pending invitations; members cannot. A send failure may return HTTP 503 after the pending invitation was saved, so the owner should use resend rather than create a duplicate.

Backend configuration requires two HTTPS frontend page URLs, but does not mandate their route names. Once pages exist, set Render's `ACCOUNT_ACTIVATION_URL=https://<frontend>.vercel.app/<chosen-activation-route>` and `EMPLOYEE_INVITATION_URL=https://<frontend>.vercel.app/<chosen-invitation-route>`. Each page must read `token` from the query string, call the corresponding backend POST endpoint, handle success and invalid/expired-token errors, and avoid retaining the token in browser history or analytics after consumption.

## API groups and staging scope

Swagger documents the request/response DTOs, success and important error statuses, owner/member authorization, pagination, multipart upload fields, binary downloads, and separate tenant/admin Bearer schemes. The primary tenant groups are `/auth`, `/users`, `/companies/current`, public `/plans`, `/subscriptions/current` and `/subscriptions/current/billing`, `/statistics/current`, `/invitations`, `/files`, `/payments`, and `/ai`. The `/admin` namespace uses separate Platform Admin credentials; the local frontend has a separate `/admin` screen. `GET /users` and employee deletion are owner-only; both owner and member may read their allowed tenant views. The billing endpoint is an internal current-period estimate, not an invoice or payment receipt.

Staging currently has `STRIPE_ENABLED=false`, `OPENROUTER_ENABLED=false`, Google OAuth unconfigured, and S3 unconfigured:

- Payment endpoints return HTTP 503 for an authenticated owner while Stripe is disabled; do not present them as working Checkout or invoices. The internal `PATCH /subscriptions/current` assignment-mode plan change can still operate without payment, so do not portray it as a paid purchase.
- `POST /ai/chat` returns HTTP 503 with code `ai_disabled`; conversation reads may still be empty/not found. Hide or disable AI chat in this integration phase.
- Google sign-in and sign-up endpoints return HTTP 503 while unconfigured. After configuration, new users complete company details through `POST /auth/google/register` and receive an activated workspace.
- File upload and S3-backed download/delete return a sanitized HTTP 503 when storage is unconfigured, after any earlier validation or authorization checks. File metadata listing can still return normally. Hide upload/download controls until S3 staging storage is enabled; never assume a 503 means an upload succeeded.

Treat 400 validation errors, 401 missing/expired/inactive authentication, 403 insufficient role or plan entitlement, 404 unavailable or unauthorized tenant resource, 409 conflicts, 429 throttling, and 503 disabled/unavailable dependencies as distinct UI states. Do not retry a mutation automatically after an ambiguous network failure. Successful provider acceptance is not proof that email reached the inbox.

## Browser CORS

Render's `CORS_ORIGIN` accepts comma-separated **exact origins**, without paths or trailing slashes. For a local Next.js frontend and one stable Vercel deployment, configure `CORS_ORIGIN=http://localhost:3000,https://<frontend>.vercel.app` in Render (add `http://127.0.0.1:3000` only if that is actually used). HTTP is permitted only for localhost; deployed origins must use HTTPS. Arbitrary Vercel preview URLs are not automatically allowed. The backend sets `credentials: false`, uses no cross-origin auth cookies for tenant APIs, and expects the Bearer header. Leaving CORS blank blocks cross-origin browser calls, though same-origin Swagger still works.

If `RESEND_FROM` uses Resend's shared `onboarding@resend.dev` testing sender, test registration with the email address associated with that Resend account; the shared sender cannot be used for arbitrary recipients. To test registration and invitations with other inboxes, either verify a sending domain in Resend or configure the backend's existing SMTP sender with Brevo on port 2525 as described in `README.md`. An account saved during failed delivery needs **Resend activation**, not another signup. No provider key or sender configuration belongs in frontend environment variables.

## Platform admin access requests

Platform admin access is separate from tenant registration. The public `/admin` screen offers **Request platform admin access**; it never creates an admin account on submission. `POST /admin/access/request` (HTTP 202) accepts `{ "fullName": "…", "email": "…" }` and optional `reason` (up to 500 characters). The response is deliberately generic for existing admins and duplicate requests. It sends a 24-hour, single-use verification link to `/admin#verify_admin_request=<token>`. The frontend removes the fragment from browser history and submits `{ "token": "…" }` to `POST /admin/access/verify`. A valid verification moves the request to `pending_review`; invalid, expired, and reused links return HTTP 400. Active platform admins receive a review notification email. Verification or notification delivery failures do not grant access.

An authenticated platform admin lists verified requests with `GET /admin/access-requests?page=1&limit=25` (separate Platform Admin Bearer token; limit 1–50). It returns `{ items, total, page, limit }`. Each item includes `id`, `fullName`, `email`, optional `reason`, `status`, and relevant timestamps; token hashes are never returned. `POST /admin/access-requests/:id/decision` accepts `{ "decision": "approve" | "reject" }` only for `pending_review` requests and returns `{ status, notificationDelivered }`. Approval emails a 24-hour one-time `/admin#setup_admin=<token>` link; rejection emails the decision and creates no account. A decision conflict returns HTTP 409. If delivery fails, the admin can retry `POST /admin/access-requests/:id/resend-setup` for approved requests or `POST /admin/access-requests/:id/resend-rejection` for rejected requests, both with an empty JSON body. Resending setup rotates the previous token.

The approved applicant submits `{ "token": "…", "newPassword": "…" }` to public `POST /admin/access/setup`; the password follows the shared new-password rule (12–72 characters, no more than 72 UTF-8 bytes, upper/lowercase letters, digit, symbol). Setup atomically creates the active platform admin account, consumes the token, and returns `{ "activated": true }`; it does not issue a JWT. The person then signs in through existing `POST /admin/auth/login`. Request creation, verification, decisions, and activation are audited. The private bootstrap command remains available for the first platform admin.
